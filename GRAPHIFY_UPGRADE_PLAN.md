## Context for the Reader

This plan treats understandability as the primary deliverable for today. The system already works, the pipelines already produce correct artefacts, and users already complete runs end to end. What is expensive is the time it takes a new contributor, or you in three months, to answer where a piece of logic lives, why two similar code paths exist, and whether a change to one workflow will break another. The upgrade translates Graphify's organizing ideas into this codebase so that those questions become cheap.

## What Graphify Is and Why It Is Relevant Here

Graphify is framed by its authors as a knowledge-graph construction toolkit that turns unstructured text into a structured graph of entities and relationships. Conceptually it provides a pipeline that ingests documents, chunks them, extracts typed entities and relations through a language model, builds a graph, persists that graph behind a storage abstraction, and then exposes query and visualization surfaces. Providers are pluggable, schemas are declarative, and each stage is independently composable rather than hidden inside a single function. For TextBro the relevance is twofold. First, Graphify's pipeline thinking is a template for restructuring our own multi-stage workflows. Second, Graphify's graph building capability can become a product feature, for example by extracting a knowledge graph from lesson text and enriching the generated HTML or enabling graph-based navigation of the content.

## Diagnosis in Graphify Terms

Viewed through Graphify's lens, the current codebase conflates concerns that Graphify keeps separate. Ingestion, prompting, generation, repair, rendering, export, persistence, and scheduling are interwoven inside the two large files `routes/runs.py` and `pages/TextToVideo.tsx`. Configuration is spread across a handwritten Python file, environment variables, and defaults embedded in individual functions. Output paths are resolved relative to the current working directory at call time, which means the filesystem contract is implicit. Two parallel implementations of the same export pipeline exist, one inline for Server-Sent Events and one queued, which drift independently. These are not defects in the product sense, they are understandability debts that Graphify's separation of ingest, extraction, build, store, and visualize is designed to prevent.

## Target Picture Inspired by Graphify

The target picture keeps every existing capability and simply reassigns it to explicit stages. Ingest becomes a small set of adapters for text, HTML, image or PDF, and YouTube inputs, each responsible only for normalizing its input into a common document model that carries the original text, project metadata, and fingerprints. Extraction becomes a dedicated service that wraps language-model interaction, including provider selection, streaming, caching with a composite key, fallback chains, and repair passes, behind a single interface that callers use without knowing retry or timeout details. Build becomes the HTML assembly and screenshot capture stage, parameterized by a first-class settings object rather than dozens of optional dictionary entries. Store becomes a repository abstraction over the current JSON-file implementation for runs, history, cache, and artefacts, so that callers depend on an interface and not on `output/runs/index.json` on disk. Orchestration becomes a scheduler that knows about queueing, single-flight deduplication, cancellation, and concurrency modes, but does not know how to generate HTML or how to render PowerPoint. The frontend mirrors this decomposition by separating the wizard shell, per-step forms, validation, draft persistence, and the event subscription that reflects backend progress. This picture borrows Graphify's insight that a pipeline is easier to understand when it reads as a sequence of named stages with typed inputs and outputs.

## Understandability as a First Class Concern

Beyond code motion, understandability requires artefacts that explain the system without requiring a full read. The first is a code knowledge graph that maps files to the entities they define and the relationships between them, such as which route enqueues which workflow and which workflow emits which event type. Graphify itself can produce such a graph from source text, and even without a live Graphify installation the same effect can be achieved by a lightweight script that parses Python and TypeScript files for imports, route registrations, and event names and emits a Graphviz or Mermaid diagram. The second is a declarative settings schema that lists every tunable, its default, its source, and the workflows that consume it, so that configuration questions are answered in one place. The third is consistent path resolution from a single root that is computed once at boot, eliminating the current pattern where every helper recomputes `output/screenshots` relative to wherever the process happened to start.

## Work Proposed for Today

The work for today is organized as a short sequence that can be completed without changing external behaviour. The early part is preparation, where a new package layout is introduced, the egress allowance for `github.com` is requested so that the live Graphify source can be pulled and pinned, and a thin settings module is added that centralizes path and model configuration behind an object that the rest of the code can import. The middle part is decomposition, where the monolithic route file is split along workflow boundaries, the shared export helper is lifted into a service that both the queued and the inline paths reuse, and the frontend wizard is broken into a shell plus per-step modules with isolated validation. The later part is Graphify alignment, where a code knowledge graph is generated and checked into `docs/code-graph.md`, the README and backend README are synchronized to the new layout, and an optional product experiment is scaffolded that runs Graphify's extraction on the input text before HTML generation to produce an auxiliary entity graph that can be rendered as a sidebar in the generated page or exported for downstream use. Each of these pieces can land independently, so that progress remains shippable even if one piece takes longer than expected.

## How the Files Move

The move that most improves navigation is to give every concept a single home. The Flask factory remains in `backend/app.py`, but route registration becomes a one-line composition of blueprints. Each workflow gets its own module under `backend/routes/runs`, with a common module for fingerprinting, canonical naming, and resume detection that is currently duplicated across handlers. Language-model interaction is consolidated under `backend/src/services/ai_service.py` so that the logic for prompt assembly, provider resolution, and repair that currently lives in `src/core/ai_client.py` is presented as a service with a narrow interface. Screenshot capture remains in `screenshot_engines` but is invoked only through the service layer. Storage access is wrapped in `backend/src/repositories/run_repository.py` and `artefact_repository.py` so that callers no longer manipulate JSON files directly. On the frontend, `pages/TextToVideo.tsx` is thinned to orchestration, while `features/wizard/steps` holds each step and `features/wizard/validation.ts` holds the per-step rules that are currently inlined. The shared `helpers` utilities are split into `services/naming.py` for canonical stems and `services/io.py` for HTML and screenshot persistence, which removes the current mixing of filesystem and naming concerns in a single file.

## Graphify Integration Options Considered

Three integration depths were considered and can be adopted incrementally. The lightest option is to adopt Graphify's architecture without adding a dependency, simply by mirroring its stage boundaries and schema-driven configuration in our own code, which already delivers the understandability benefit. The middle option is to add Graphify as a sidecar that ingests lesson text and emits an entity-relationship graph alongside the existing HTML, without altering the primary pipeline, so that the graph can be inspected, visualized, or used to enrich the HTML with linked definitions. The deepest option is to make the graph a first-class input to HTML generation, where detected entities drive the section structure or where the graph is offered as an additional output format for publishers. The lightest option is recommended for today, the middle option is a good next increment once egress is opened and the Graphify package can be evaluated against our provider and storage choices, and the deepest option should only be pursued after the middle option has been validated with real lesson material.

## Risks and Mitigations

The principal risk for today is the blocked egress to `github.com`, which prevents pinning a specific Graphify revision and inspecting its storage interfaces directly. The mitigation is to proceed with architecture-only alignment and to gate any code dependency on an allowlist change or a vendored snapshot that can be reviewed offline. A second risk is churn in the large files that are being split, which can produce noisy diffs. The mitigation is to perform the split as pure moves with no logic changes, and to defer logic cleanup to follow-up commits that are then trivially reviewable. A third risk is the implicit filesystem contract, where tests or scripts rely on the current working directory being `backend`. The mitigation is to introduce the centralized path object early and to add a small startup assertion that verifies expected directories are writable, which the existing `/preflight` check already partially provides.
